# General-purpose self-hosted platforms for a secure Redis browser

Research date: **22 October 2026**. Web research only: no repositories cloned, dependencies installed, applications run, or live Redis connections tested. Product documentation, public source viewed on the web, licenses, and maintainer/security-coordinator advisories are the evidence. The products already evaluated in the brief are excluded.

## Recommendation and ranked top three

These are **evaluation priorities, not security approvals**. No candidate is proven by this research to satisfy every requirement. Platform RBAC and an audit-log checkbox do not establish Redis command/key authorization or complete command auditing.

1. **CloudBeaver Enterprise — first commercial evaluation for an existing web database workbench.** Its commercial Redis driver, centralized connections, SSO, team permissions, and query-management/audit facilities are the closest mature packaged platform proposition. Redis is not a Community feature. The important qualification is that the detailed Redis guide describes DBeaver's driver, not a demonstrated CloudBeaver web feature matrix: obtain a web demonstration of key editing, command execution, TLS certificate verification, cluster routing, and Redis query audit coverage before selecting it. Its JVM backend also misses the Node preference. [Enterprise product](https://dbeaver.com/cloudbeaver-enterprise/), [Enterprise release notes containing Redis fixes](https://dbeaver.com/cloudbeaver-enterprise-release-notes/), [Redis driver guide](https://dbeaver.com/docs/dbeaver/Redis/).

2. **ToolJet — best Node/TypeScript platform for building a controlled Redis UX.** It documents server-held encrypted datasource credentials and Redis TLS with CA/client certificates. Build forms, type-specific views, command explanations, and approved operations; this is an application project, not a ready Redis browser. Paid SSO/auditing and the platform's significant attack surface are costs. Check the selected self-hosted plan explicitly; Team and Enterprise packaging differs. [Redis connector](https://docs.tooljet.ai/docs/data-sources/redis/), [security](https://tooljet.com/security), [plans](https://tooljet.com/pricing).

3. **DbGate Team Premium — strongest documented ready-made Redis UX, with a consequential security review.** Key browsing, type-aware editing, streams, and command console are explicitly documented; cluster support is Premium, and team identity/RBAC/audit are paid. This could overtake CloudBeaver after validation, but multiple published RCE/file-access advisories make isolation and a full patch review essential. [Redis features](https://www.dbgate.io/features/redis-gui/), [Team Premium](https://www.dbgate.io/editions/team-premium/), [maintainer advisories](https://github.com/dbgate/dbgate/security/advisories).

**Additional OSS candidate: LibreDB Studio**, particularly if an owned TypeScript codebase matters more than maturity. Managed seeds can keep credentials off the browser, but ordinary connections do not provide that guarantee. Its Redis provider explicitly lacks Cluster/Sentinel, subscriptions, and a Redis read-only guard. Consider it a codebase evaluation, not an already established security platform. [Managed seeds](https://github.com/libredb/libredb-studio/blob/main/docs/SEED_CONNECTIONS.md), [Redis limitations](https://github.com/libredb/libredb-studio/blob/main/docs/providers/redis.md).

## How to read the comparison

- **Native browser** means a usable key/type UI ships with the product. A Redis connector merely enables us to build one.
- **Console** means request/response Redis commands in a web editor; it does not imply a persistent redis-cli session, transactions tied to a session, blocking reads, MONITOR, or subscriptions.
- **U** means unverified in the cited official material, not proven absent. A library supporting a feature is insufficient evidence that its product connector exposes it.
- Common Redis types below mean strings, hashes, lists, sets, and sorted sets. Streams/JSON are identified separately. TLS means backend-to-Redis TLS; browser HTTPS alone is insufficient.
- Server-side execution does **not** automatically mean server-only credentials. Browser-created connection forms, exports, resource permissions, admin APIs, and client storage need separate review.

Footprint is qualitative operating burden, not an SBOM or measured image size. Components vary by version and enabled features. **No CVE found means only that this bounded search did not verify one**; it is not evidence of safety. Advisories may span other database drivers but still matter when those routes ship in the same Redis-facing backend. ## What a non-CLI developer would actually get

**Ready-made inspection/editing:** DbGate offers the clearest documented path from finding a key to viewing its type/TTL and editing a value, including streams. CloudBeaver and WhoDB deserve browser demonstrations because their general multi-database feature lists are less specific about Redis. Beekeeper is usable but violates the browser/backend architecture.

**Purpose-built safe workflows:** ToolJet or Retool can make common work easy: search by prefix, inspect a session/cache entry, edit a hash field, delete a selected key, set TTL, or compare values. Those screens do not exist just because a connector exists. Builders must implement bounded SCAN, paging of large values, binary/JSON rendering, type-aware validation, mutation previews and understandable Redis errors. Appsmith is only an option here through a separate TLS-capable API.

**Monitoring:** Grafana provides immediately understandable charts and some query forms, plus a real browser CLI in Redis Application. Redis Explorer is an Enterprise-cluster management app, not the missing universal key browser. Streaming charts are not evidence of a general interactive pub/sub debugger.

## Selection gates specific to this security requirement

These are the concrete unknowns to resolve for the top candidates, not activities performed in this research:

1. **Prove server-only secrets.** Configure production connections as operator-owned resources; inspect connection-list/export/admin responses, browser storage and error paths using an ordinary user's session. Never make developers paste production Redis URLs. Verify password rotation without reissuing secrets to users.
2. **Prove authenticated TLS.** Reject invalid CA/hostname, support the organization's client certificate needs, and demonstrate TLS on every Cluster/Sentinel hop. `rediss://`, a TLS toggle, and “skip verify” are not interchangeable guarantees.
3. **Separate app access from Redis authority.** A generic command box can bypass a carefully designed form if it shares a powerful credential. Use distinct server-held Redis ACL users/connections for reader/operator/admin roles, key-pattern/command restrictions, and backend authorization on every operation. Redis recommends ACLs over command renaming. [Redis security](https://redis.io/docs/latest/operate/oss_and_stack/management/security/).
4. **Demonstrate command audit.** Require identity, connection/environment, command category, outcome and time; agree how sensitive arguments/values are redacted. Platform configuration logs or personal query history are insufficient. Test command console, generated mutations, scripts and imports, not just button clicks.
5. **Qualify stateful operations separately.** Pub/sub subscriptions, blocking stream reads, transactions, database selection and Cluster redirects need connection/session designs beyond ordinary query connectors. “Any Redis command” marketing does not prove these work safely.

If both **fully OSS governance** and **Node/TypeScript** are mandatory, none of the mature platforms above is a verified drop-in winner. LibreDB's managed mode deserves focused source/security review; otherwise a tightly scoped owned Redis API plus an existing internal-tool frontend is the more controllable design, with the explicit cost of building the Redis UX and enforcement.
