# Redis access gateways and governance platforms

Research date: 2026-10-22. Method: web-only review of vendor documentation, public source viewed in the browser, licenses, release notes and security advisories. No software was cloned, installed or executed. This is a capability assessment, not a penetration test. Version-dependent gaps and uncertain claims are marked explicitly.

## Decision

The hypothesis is partly correct: existing platforms can supply identity, credential custody, short-lived access and audit infrastructure. **None reviewed is a verified, complete substitute for a Redis-aware backend that enforces command, key, response-size and disclosure policy for a custom browser UI.** A network gateway granting a session is not automatically a command firewall; logging a command is not the same as masking its result.

The two strongest combinations are:

1. **Custom browser UI + policy/execution backend + Vault Redis dynamic credentials + Redis ACLs.** Best fit when owning the security boundary matters most. Vault supplies credential lifecycle; the backend supplies developer UX, command authorization, result masking and attributable command audit.
2. **Custom UI/backend + commercially licensed Infisical PAM gateway + Redis ACLs.** Most interesting existing access platform because Redis browser access, credential injection and session logging already exist. However, its current source explicitly excludes Redis from command-blocking policy. Treat custom UI integration and command enforcement as engineering work, not a configuration-only solution.

If a ready-made UI is acceptable, evaluate **Bytebase** and **NineData** before building: both have real Redis command execution in a browser; NineData also documents visual key editing and Redis-specific development-policy checks. **Archery** is the clearest permissively licensed workflow-oriented starting point, but has no Redis result masking. **Teleport** is attractive when already deployed company-wide, but adds substantial infrastructure without replacing Redis command policy or supplying a documented Redis web console. Sources and qualifications follow.

## Product findings

### Teleport

**License.** Do not describe current official Community Edition distributions simply as OSS. Since v16, prebuilt binaries/images use a commercial license: free company use is restricted by employee/revenue thresholds and embedding/resale restrictions. The public source remains **AGPLv3**, so compiling it is an OSS route with AGPL obligations. This does not unlock proprietary Enterprise functionality. [Official license-change announcement](https://goteleport.com/blog/teleport-community-license/).

**Redis and web UI.** Teleport has a genuine Redis Database Service and a separate Cluster mode. Self-hosted onboarding uses `rediss://`, verified server certificates and client mTLS; the documented flow still creates Redis ACL users/passwords and has the client issue `AUTH`. Therefore, “Teleport eliminates all Redis passwords” is an incorrect reading of its certificate-based access story. A custom backend can retain those passwords server-side. Standalone protocol limitations include `HELLO`, `PUNSUBSCRIBE`, `SSUBSCRIBE` and `SUNSUBSCRIBE`; Cluster has additional command restrictions. [Redis enrollment](https://goteleport.com/docs/enroll-resources/database-access/enrollment/self-hosted/redis/), [Cluster enrollment](https://goteleport.com/docs/enroll-resources/database-access/enrollment/self-hosted/redis-cluster/).

Its browser UI manages resources, audit and sessions. The browser database-session guide documents PostgreSQL-era support expanded to CockroachDB and MySQL/MariaDB; **Redis is not documented as a browser-query protocol**. Redis access is through `tsh db connect`, a local tunnel or a compatible client, not a verified browser Redis/key explorer. [Web UI guide](https://goteleport.com/docs/connect-your-client/teleport-clients/web-ui/).

**Governance.** Resource labels and allowed database users are useful RBAC. Object permissions currently apply to PostgreSQL; `db_names` enforcement is limited to PostgreSQL, MongoDB and Spanner, so it must not be relied upon to constrain Redis logical DBs. No Redis command/key policy DSL was established; enforce those through Redis ACLs and the application backend. [Database access controls](https://goteleport.com/docs/enroll-resources/database-access/rbac/).

Database session/query audit is supported, with JSON playback/export and audit viewing in the web UI. The FAQ distinguishes database-session listing from browser playback, which it describes for PostgreSQL. Do not equate database audit with a Redis result transcript or dynamic data masking; Redis response masking was not verified. [Database FAQ](https://goteleport.com/docs/enroll-resources/database-access/faq/), [database audit events](https://goteleport.com/docs/reference/audit-events/database/).

**SSO/deployment/integration.** Community supports GitHub SSO, while OIDC/SAML require Enterprise; full JIT access requests also have an Enterprise boundary. Self-hosting means Auth/Proxy services, database agents, CA lifecycle, durable audit storage and HA planning: high complexity relative to one Redis UI. A backend can connect through a server-side tunnel, but a shared machine identity makes Teleport see the backend rather than each human unless delegated identities are designed explicitly. This is an architectural inference, not a turnkey vendor recipe. [SSO](https://goteleport.com/docs/get-started/sso/), [authorization](https://goteleport.com/docs/reference/architecture/authorization/).

### HashiCorp Boundary

**License and support.** Current Boundary source uses **BSL 1.1**, a source-available license, not an OSI open-source license for the current release; version-specific conversion provisions do not make the current edition OSS. Redis is supported as a **TCP target**, with a dedicated `boundary connect redis` helper invoking `redis-cli`. It is wrong to say Redis is wholly unsupported, but equally wrong to call this a Redis-aware governance proxy. [License](https://github.com/hashicorp/boundary/blob/main/LICENSE), [Redis connect command](https://developer.hashicorp.com/boundary/docs/commands/connect/redis).

**Credential boundary.** Boundary distinguishes brokering (credentials returned to the client) from injection (hidden from the end user). Its current credential docs explicitly say TCP targets cannot use injected application credentials. A Redis CLI accepting brokered password credentials is not server-side Redis AUTH injection. There is no verified browser Redis console/key browser, command allow/deny list or Redis result masking. [Credential workflows](https://developer.hashicorp.com/boundary/docs/credentials).

**Audit/SSO/deployment.** OIDC identity integration and target RBAC suit network access. Audit events cover controllers/authentication/worker-controller requests, not decrypted Redis commands; audit emission must be enabled explicitly. Audit-field sanitization concerns Boundary event material, not Redis results. Production self-hosting adds controllers, workers, PostgreSQL and KMS integration, with Vault often added for credentials: medium-high complexity. Enterprise session recording/injection features must not be assumed to apply to Redis TCP. [Audit guidance](https://developer.hashicorp.com/validated-designs/boundary/administration-guide/audit-log-management), [event configuration](https://docs.hashicorp.com/boundary/docs/configuration/events).

**Custom UI:** usable as private connectivity for the backend. Backend Redis credential custody, SSO session mapping, command authorization, masking and audit remain ours. Low incremental value unless Boundary is already the corporate network access standard.

### StrongDM — commercial reference only

StrongDM explicitly supports Redis 6+ with standard Redis clients, GUI clients and application drivers through gateways/relays, providing centralized credential management and access controls. Its documented Redis connection journey uses the desktop client/CLI; a Redis browser query console/key explorer was not established. [Redis resource documentation](https://docs.strongdm.com/admin/resources/datasources/redis).

The platform offers SSO/RBAC, query/activity logs and configurable log destinations/encryption. Generic OIDC and SAML SSO integrations are documented. Those logs are security-sensitive records themselves. Enterprise Cedar policies include fine-grained database-action enforcement, but the examined policy documentation specifically demonstrates PostgreSQL actions; **do not infer Redis GET/SET/key-prefix enforcement from the general PBAC label**. Redis result masking was not verified. [SSO](https://docs.strongdm.com/admin/principals/sso), [logging](https://docs.strongdm.com/admin/audit/logs), [Enterprise policy scope](https://www.strongdm.com/docs/admin/policies/).

Deployment is medium complexity: commercial control plane plus reachable gateway/relay nodes and client/service-account lifecycle. A custom backend could use a standard Redis driver through its access path, but a shared service account loses human attribution unless deliberately mapped. Its management API is not itself a generic HTTP Redis execution API. Commercial identity/session integration and data residency terms require agreement. [API reference](https://www.strongdm.com/docs/api).

### Bytebase

**License/features.** Bytebase is open-core: MIT for qualifying portions, but `enterprise` directories and feature/permission/role/plan-enablement code are subject to its commercial boundary. Current pricing puts Google/GitHub SSO in Pro and OAuth2/OIDC/LDAP, custom roles, approvals, JIT access and DDM in Enterprise; audit logs have Pro retention versus Enterprise unlimited retention. A free SQL editor is not a free full governance edition. [License](https://github.com/bytebase/bytebase/blob/main/LICENSE), [edition comparison](https://www.bytebase.com/pricing/).

**Redis reality.** Public driver source supports standalone, Sentinel and Cluster with server-side credentials/TLS, parsing Redis command lines and executing them through go-redis. Query results are returned as structured rows; cluster execution can target one or all nodes. This is actual browser command execution through SQL Editor, not merely an instance inventory. The reviewed evidence does not establish an Insight-style key tree/type editor or full interactive redis-cli semantics. [Redis driver](https://raw.githubusercontent.com/bytebase/bytebase/main/backend/plugin/db/redis/redis.go).

Read-only classification is real: release notes specifically fix RedisJSON/module read commands being blocked in SQL Editor, exports and JIT requests. That does not prove a configurable per-role Redis command allow/deny list. Generic column-oriented masking claims are insufficient evidence for masking arbitrary Redis strings, hashes or serialized objects; **Redis-specific response masking remains unverified**. [Redis release notes](https://github.com/bytebase/bytebase/releases), [DDM description and enforcement boundary](https://www.bytebase.com/dynamic-data-masking/).

**Deployment/custom UI.** Medium complexity: self-hosted application plus durable metadata, identity and audit integrations. It is a governed query application, not a general RESP proxy. Prefer its existing UI if it passes a Redis-specific evaluation. For a replacement frontend, call governed query endpoints with the actual user identity; establish API stability and confirm query/export/admin-mode checks are identical. Its broad editor/governance positioning is documented, but this custom integration is an architectural proposal. [SQL Editor](https://www.bytebase.com/sql-editor/).

### Archery — hhyo/Archery

**License/UI.** Apache-2.0 OSS. The feature matrix lists Redis querying and execution, but not the MySQL-style automated audit capability. The query module nevertheless has approval workflows for obtaining query access, database-level permissions and query logging. Distinguish **access approval / change tickets** from automated Redis semantic safety review. Redis masking is explicitly marked unsupported. [Repository and feature matrix](https://github.com/hhyo/Archery), [query workflow documentation](https://archerydms.com/modules/query/).

**Exact command behavior.** Current Redis engine source has separate hard-coded query and execution command lists. Queries include GET/MGET, hash/list/set/zset reads, TTL/TYPE, SCAN and stream reads. KEYS, INFO, CONFIG GET and ACL inspection are commented out of query permission. A key-preview helper scans up to 100 keys. Connections support username/password, Cluster and an SSL flag. `query_masking` returns the original result unchanged. The query row limit slices results after execution, so it is not a Redis-side memory/work limit. These are observations of current source, not proof of all tagged releases. [Redis engine source](https://raw.githubusercontent.com/hhyo/Archery/master/sql/engines/redis.py).

LDAP integration is listed; full OIDC/SAML SSO was not established in the examined docs. Deployment is medium-high: Django application, metadata database, workers/cache and optional SQL-audit ecosystem components; Redis-only scope can avoid unrelated SQL components after validating dependencies. A custom frontend could reuse the backend/query workflow, but must not invoke the engine directly and skip its surrounding permission and logging layers. The Apache license makes modification comparatively straightforward; keeping the fork secure is our responsibility. [Project dependencies](https://github.com/hhyo/Archery).

### Yearning

AGPL-3.0 OSS. The project's own description is a MySQL SQL-audit platform with SQL/query audit, source/database permissions, sensitive-field anonymization and RBAC. **No primary evidence of Redis as a governed target was found.** An internal Redis cache, dependency or future roadmap would not count. It therefore provides no verified Redis web console, key browser, command policy, Redis masking or gateway API for this requirement. LDAP/login integrations and the SQL UI do not change that conclusion. Operational footprint is comparatively modest, but adopting it for Redis would mean developing a new database integration. [Official repository](https://github.com/cookieY/Yearning).

### CloudQuery 询盾, and the naming trap

The Chinese DMS product at **cloudquery.club** explicitly lists Redis among managed databases and advertises centralized operation control, desensitization, auditing and analysis. Its community distribution is not evidence of an OSS license; no OSI license/source grant was established. Exact Redis command coverage, key browsing, per-command policy, result masking, SSO protocols and stable execution API all remain unverified. Obtain a Redis-specific demonstration and written edition matrix before shortlisting. [Vendor product page](https://cloudquery.club/h-col-104.html).

Self-hosted deployment uses a Docker-based stack and installer: medium complexity, with vendor-controlled upgrades. The reviewed material is insufficient to recommend it as the security core for a custom UI. [Vendor deployment guide](https://cloudquery.club/sys-nd/96.html).

This is **not cloudquery.io**, whose official quickstart concerns source/destination data synchronization. That CloudQuery is a data-integration product, not a Redis access-governance gateway. Do not borrow its open-source reputation, integrations or CVE record for 询盾. [CloudQuery data-integration docs](https://www.cloudquery.io/docs/cli/getting-started).

### Similar DMS platforms with verified Redis support

**Alibaba Cloud DMS.** Proprietary managed service, not an OSS component we control. Redis has a published supported-command list for SQL Console and tickets, and DMS metadata includes Redis keys/types. Security hosting takes custody of database credentials; access permissions and workflows are available. The precise mapping of Redis commands to configurable security rules needs qualification; relational DDL/DML rule examples are not proof of a Redis command firewall. Redis value masking was not established. [Redis commands](https://www.alibabacloud.com/help/en/dms/syntax-support-for-redis), [metadata and controls](https://www.alibabacloud.com/help/en/dms/product-overview/terms/), [security hosting](https://www.alibabacloud.com/help/en/dms/product-overview/security-hosting).

Deployment is low-medium for the SaaS control plane but private connectivity and cloud IAM remain. SSO would be through Alibaba's account/RAM federation ecosystem, rather than an independently embedded OSS login module. Custom UI integration would depend on DMS APIs and their coverage; no transparent Redis gateway with proven Redis masking was verified. This is a reference architecture/product alternative, especially for existing Alibaba customers. [DMS permission model](https://www.alibabacloud.com/help/en/dms/permissions/).

**NineData.** Proprietary with free Community and commercial DevOps tiers. Unlike many generic SQL platforms, its Redis documentation establishes both a command editor and visual key browsing/editing, TTL changes, history and Cluster node selection. Organization-mode commands are checked against administrator development policies and blocked when noncompliant; administrator mode can bypass standardization/approval flows. Thus admin access is an explicit insider-risk boundary. [Redis-specific console documentation](https://docs.ninedata.cloud/en/sqldev/sqlconsole/redis_console/).

The platform advertises audit, sensitive-data protection, SSO and MFA, with edition-dependent entitlements. **Redis-specific masking and the exact configurable command rules are not sufficiently established** by the broader feature page. SaaS is relatively simple; private gateways/on-prem enterprise deployment add vendor integration. Its OpenAPI presence does not prove a public execution API preserves all console policies. Reusing its existing UI is more credible than assuming it can be our invisible backend. [Feature/edition page](https://ninedata.cloud/sqldev), [security workflow overview](https://docs.ninedata.cloud/resources/use-cases/security-and-compliance/).

### JumpServer

**License/surface.** GPLv3 core. Its published component matrix specifically gives Redis a **KoKo Web CLI** in the community offering, no Chen Web GUI, and a **Magnus protocol proxy under X-Pack**. Remote application/database applets are a separate commercial route, not a native Redis key explorer. Browser-only redis-cli-style access is therefore a real reuse option, while raw RESP integration for our backend has an enterprise component boundary. [Core license](https://github.com/jumpserver/jumpserver), [vendor database/component matrix](https://fit2cloud.com/jumpserver/documents/introduce-jumpserver_202507.pdf), [Redis connection guide](https://kb.fit2cloud.com/?p=ebcbdf3d-420f-4d13-a8a5-aa5a164aa67e).

**Controls.** Command filters support command/regex matching bound to users, assets and accounts, with allow/deny/approval/alert actions. **Unmatched commands are allowed**, so a deny-list configuration is not default-deny protection. The generic filter documentation does not prove identical Redis enforcement on Web CLI, applet and Magnus paths; test each selected path, especially pipelines and AUTH changes. No Redis value masking was established. [Command filter semantics](https://docs.fit2cloud.com/jumpserver/v3/guide/admin/permission/cmd_acls/).

SSO protocols include LDAP, SAML, OIDC and CAS at product level; obtain a current community/enterprise entitlement matrix for the required connector. Session/command audit is a central product capability, but recording Redis values can itself create a data repository. Deployment is high complexity for a Redis-only use: PAM core, web frontend, KoKo and metadata/cache services, optionally Magnus and applet hosts. Reuse the terminal if that meets UX needs; do not automate typing into a terminal as a custom UI's Redis API. [Vendor authentication/features](https://www.jumpserver.com/features).

### Infisical: Redis PAM and dynamic secrets are distinct products

**License.** MIT core excludes `ee/`, which uses the proprietary Infisical Enterprise License requiring a valid production subscription. The PAM session implementation is under `backend/src/ee`; do not infer that its Redis gateway/browser functions are MIT merely because the repository has an MIT badge. Current pricing has paid PAM Pro/Enterprise offerings; self-hosted entitlement should be confirmed explicitly. [Root license](https://github.com/Infisical/infisical/blob/main/LICENSE), [EE license](https://raw.githubusercontent.com/Infisical/infisical/main/backend/src/ee/LICENSE.md), [PAM pricing](https://infisical.com/pricing).

**PAM capabilities.** Current README advertises browser access to Redis. Indexed vendor documentation describes an interactive Redis REPL and server-side WebSocket execution through a gateway, while the CLI starts a local proxy whose upstream authentication is handled for the user. Redis session tracking includes executed commands. Browser key browsing/editing comparable to Insight was not established. Caveat: the old detailed Redis/Web Access URLs returned 404 on direct retrieval, although their indexed content remained accessible; the current README corroborates browser Redis support, but old fixed timeout/limit values should not be relied upon. [Current README](https://github.com/Infisical/infisical/blob/main/README.md), [indexed Redis PAM guide](https://infisical.com/docs/documentation/platform/pam/getting-started/resources/redis), [current CLI documentation source](https://github.com/Infisical/infisical/blob/main/docs/cli/commands/pam.mdx).

**Critical policy distinction.** Pricing advertises command blocking, but current `pam-policies.ts` applies it only to SSH, Snowflake and ClickHouse — **Redis is excluded**. Redis is included by the account-type helper for session-log masking. The session service sends applicable policy rules to gateways. This establishes configuration support for Redis log masking, not tested end-to-end enforcement or masking of data returned to the user. Use Redis ACLs and backend policy for command/key restrictions. [Policy applicability source](https://raw.githubusercontent.com/Infisical/infisical/main/backend/src/ee/services/pam/pam-policies.ts), [masking applicability](https://raw.githubusercontent.com/Infisical/infisical/main/backend/src/ee/services/pam/pam-enums.ts), [session service](https://raw.githubusercontent.com/Infisical/infisical/main/backend/src/ee/services/pam-session/pam-session-service.ts).

**Dynamic secrets.** Separately, Redis dynamic secrets create users on demand with configurable statements, TTL/max TTL, lease renewal/revocation and CA/SSL options. This can supply backend-only, least-privilege Redis credentials. The dashboard can display generated credentials, so granting developers direct lease-reading permission would violate the intended custody model; grant that ability only to the execution backend. Dynamic-secret lease audit is not a log of Redis commands subsequently executed. [Redis dynamic-secret guide](https://infisical.com/docs/documentation/platform/dynamic-secrets/redis).

**SSO/deployment/integration.** Paid platform plans include SAML; LDAP/SCIM and audit streaming have higher-tier boundaries. Do not assume buying one product unlocks every identity capability in another. Self-hosted app, PostgreSQL/cache, encryption-key custody and gateway/relay services imply medium-high complexity. Existing PAM UI is easiest to reuse. A custom backend may use its brokered session path, but must preserve human identity; current source explicitly refuses machine sessions on accounts requiring human MFA or approval. A single broad service identity is not a substitute for delegated human sessions. [Pricing](https://infisical.com/pricing), [session authorization source](https://raw.githubusercontent.com/Infisical/infisical/main/backend/src/ee/services/pam-session/pam-session-service.ts).

### HashiCorp Vault

Current Vault is BSL 1.1 source-available; Enterprise is commercial. The Redis database secrets plugin supports dynamic roles, static roles, root credential rotation and TLS/CA configuration. Dynamic roles provision Redis ACL rules. It provides **no Redis command console, key browser, data-path proxy or result masking**: its UI manages secrets, not Redis data. [Vault license](https://github.com/hashicorp/vault/blob/main/LICENSE), [Redis secrets engine](https://developer.hashicorp.com/vault/docs/secrets/databases/redis).

Vault policies govern who may obtain a role's credentials; Redis ACLs enforce commands/keys once connected. OIDC login is supported. Audit devices record Vault API activity, not the subsequent Redis session. HMAC/redaction of secret fields in Vault audit is unrelated to masking Redis responses. [OIDC](https://developer.hashicorp.com/vault/docs/auth/jwt), [audit devices](https://docs.hashicorp.com/vault/docs/audit).

Operational complexity is medium-high if new: HA storage, seal/unseal/KMS, audit sinks and lease/revocation monitoring. If already operated, its HTTP credential API is an excellent foundation for our backend. Do not assume TTL alone kills established connections or that revocation works during an outage; verify the actual plugin/server behavior and explicitly terminate backend sessions on expiry.

### Envoy Redis proxy and RBAC

Apache-2.0 OSS. Envoy offers a Redis protocol filter, Cluster routing, prefix routing, distinct downstream/upstream authentication and an external Redis authentication hook. It is neither a web console nor a key explorer. Command compatibility depends on the selected release; the support list is a routing/implementation boundary, not an organization-defined security allow list. [Redis architecture](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/other_protocols/redis), [authentication/filter configuration](https://www.envoyproxy.io/docs/envoy/v1.37.1/api-v3/extensions/filters/network/redis_proxy/v3/redis_proxy.proto).

**RBAC caution:** Envoy's network RBAC filter authorizes connections using network/authenticated-principal context. The Redis external-auth provider is invoked on AUTH, not on each arbitrary Redis command. Neither should be sold as native per-user GET/SET/key-pattern authorization. No built-in Redis result masking or complete human-attributable command-audit workflow was established. Metrics and network access logs are not equivalent. [Network RBAC](https://www.envoyproxy.io/docs/envoy/v1.37.7/configuration/listeners/network_filters/rbac_filter).

SSO needs a separate HTTP identity layer/custom auth service. Proxy deployment alone is moderate complexity, but adding policy, certificates, identity and compliance audit makes the complete system high complexity. Good fit for existing Envoy operators needing network isolation or routing; weak reason to introduce Envoy solely as a Redis security product. Keep upstream ACLs and custom backend checks even if Envoy is used.

### Predixy and similar Redis-aware proxies

**Predixy:** BSD-3-Clause; supports Sentinel/Cluster, SCAN, transactions in limited modes, scripting and pub/sub. Extended AUTH provides read/write/admin modes and read/write key-prefix restrictions, not a verified arbitrary per-command policy DSL. Its sampled operational logging is not a full SSO-linked immutable audit system. No browser UI, SSO or result masking is established. [Repository/features](https://github.com/joyieldInc/predixy), [authority configuration](https://github.com/joyieldInc/predixy/blob/master/conf/auth.conf).

The maintainer stated TLS was unsupported in a public issue; no current native TLS feature was established in this review. It therefore fails the verified `rediss://` requirement without additional TLS components and qualification. Deployment is light as a proxy, but the missing security stack makes it a poor first choice. [TLS issue](https://github.com/joyieldInc/predixy/issues/173).

**Camellia Redis proxy:** MIT, Netty/Java-based; supports TLS on both legs, standalone/Sentinel/Cluster, SCAN, module commands and HTTP access. It has request/response interception plugins, IP filtering/rate limiting/namespaces and a Spring Boot integration path. No browser Redis console, enterprise SSO, immutable human audit or turnkey result masking was verified. A custom plugin can implement command policy and response handling, but that is our security code. Deployment is moderate (JVM/proxy replicas and routing configuration); governance work remains high. Particularly relevant for a Spring/Java team wanting to extend an existing Redis parser/proxy rather than write one. [Project/license](https://github.com/netease-im/camellia), [proxy features/plugin model](https://github.com/netease-im/camellia/blob/master/docs/camellia-redis-proxy/redis-proxy-en.md).

Twemproxy/Codis-style sharding proxies were not elevated to governance candidates: sharding and client compatibility do not establish SSO, command audit or disclosure controls. RedisShake is excluded as requested.

## Promising combinations

### 1. Own the execution boundary; use Vault for credentials

```text
Browser → SSO-authenticated UI API → command policy/execution backend → TLS Redis
                                      ↕
                            Vault Redis credential leases
                                      ↓
                       independent command audit / SIEM
```

This is an architectural recommendation based on the capabilities above, not an off-the-shelf integration claim.

- **Identity:** authenticate the human through the company IdP; bind tenant/team/environment and approval state to every request. The browser receives an application session only, never a Redis password, URI containing credentials, Vault token or reusable Redis tunnel credential.
- **Credentials:** backend authenticates to Vault with a workload identity. Select only preconfigured roles derived from approved user access; do not let a user supply a Vault role or arbitrary Redis endpoint. Issue short-lived, unique credentials per user/session or narrowly scoped authorization context. Keep credentials in backend memory and revoke/close on session end.
- **Enforcement:** Redis ACLs provide the independent command/key restriction. The backend adds default-deny command/subcommand checks, argument rules, environment restrictions, approvals, quotas, output limits and masking. Never rely solely on read/write command categories or a regex over a command string. Redis ACLs support command/category and key/channel rules, but are not result-masking or complete successful-command audit facilities. [Redis ACL documentation](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/).
- **UX:** implement a smart command editor, explanations, bounded SCAN browsing and explicit typed views. Decode Spring/Jackson/JDK or Node application payloads as inert data; never deserialize arbitrary server values into executable application objects. Binary-safe arguments/results and explicit encodings are necessary; a whitespace-split shell imitation is insufficient.
- **Audit:** log verified human, resource, role/lease identifier, normalized command, authorization decision, approval reference, latency, result status and bytes returned. Redact credential-bearing/sensitive arguments; do not store raw values by default. Separate policy administrators, credential administrators and audit readers; export to append-only storage outside execution-service administration.

**Why this leads:** least dependence on gateway-specific UI internals; direct control over insider exfiltration policy and data presentation. **What remains to build:** the security-critical command execution/masking layer and developer UX. Vault does not provide those pieces. If Vault is already operated, this avoids adding a second full PAM stack.

### 2. Reuse Infisical PAM; add the developer UI and Redis policy

```text
Browser → custom API / policy backend → per-human PAM session → Infisical Gateway
                                  ↘ audit correlation                 ↓ TLS
                                     SIEM                       Redis ACL account
```

First evaluate the existing Redis browser REPL: it may cover the initial CLI experience without a new frontend. For a custom UI, prefer a supported, identity-preserving session interface. Agree the contract with the vendor; do not assume private WebSocket endpoints are stable APIs.

**Reuse:** credential custody/injection, account authorization, time-limited access, approvals/MFA, session tracking and log masking, subject to subscription and selected release. **Build/retain:** Redis-specific default-deny command policy, key-prefix selection, disclosure masking, quotas, safe browsing and rich data views. Current Infisical policy source excludes Redis command blocking, so Redis ACLs are mandatory and the stock REPL alone does not satisfy the requirement.

Do not place all humans behind an unrestricted machine account. Current service code rejects machine identities for human-MFA/approval-gated accounts; integration must preserve the human approval/session model instead of disabling it. A viable alternative is using Infisical **dynamic secrets only** in the first architecture, but that forfeits PAM's data-path/session audit. Treat these as different designs and cost them separately.

**Why this is promising:** it already owns more of the browser/PAM experience than Teleport or Boundary for Redis. **Risks:** commercial self-hosted license, rapidly evolving APIs/docs, exact gateway logging behavior, and the need for our own Redis policy. Source evidence is enough to justify a focused proof of concept, not production approval.

## Required proof before choosing either combination

These checks are proposed evaluation criteria; none were executed during this web-only research.

1. **Custody and network isolation:** inspect browser requests, WebSocket frames, error payloads, exports and source maps for credentials; Redis accepts traffic only from approved execution/gateway hosts with verified TLS, including Cluster-discovered nodes and Sentinel paths.
2. **Human attribution:** two users with different grants must stay distinguishable in gateway and application audit; no cross-user pooling of authenticated Redis connections. Revocation, offboarding, session expiry and approval expiry must terminate access, including already-open connections.
3. **Command bypasses:** mixed case, leading whitespace, quoted/binary args, pipelines, MULTI/EXEC, AUTH/HELLO/SELECT, EVAL/EVALSHA/FCALL, Redis modules and unknown commands. Evaluate each against parsed command structure and upstream ACLs. Prevent switching to a more privileged account or bypassing approved data scope.
4. **Data leakage:** SCAN/key names, DUMP/RESTORE, hashes/streams, JSON/Search commands, MONITOR, SLOWLOG, pub/sub and diagnostic commands can expose data through different paths. Validate both response masking and audit redaction; log masking alone does not limit what a user sees.
5. **Insider exfiltration and availability:** cumulative byte/key limits, bounded collection reads, pagination deadlines, large values, blocking commands, export restrictions and access alerts. A read-only user can still extract all permitted data without these controls.
6. **Failure and operator boundaries:** closed behavior on authorization/audit failure, unavailable secret manager, delayed lease revocation, gateway restart and backend cancellation. Test whether policy administrators can grant themselves production access and whether audit evidence survives their actions.
7. **Release/licensing evidence:** pin supported versions; obtain current edition entitlements and security patch commitments. Recheck licenses for the exact deployed artifacts, not only repository badges. Complete a Redis-specific security review of the selected backend/gateway path.
